01The problem

Between error detection and error correction.

The starting point was a production planning system in real use. Its planning states come as snapshots from the ERP system: orders, material requirements, machine allocation, employee qualifications – connected to almost every area of the company.

The existing planning system detects such errors, but cannot fix them on its own. The real challenge is to understand the relationships and derive a correction that is right from a domain perspective.

A practical example

One snapshot, three to five reported errors.

Before · by hand 2–6 hours
  1. Read the error message and find the affected spot among more than 200,000 entries
  2. Check relationships to articles, resources and work plans
  3. Derive the correct value and change it by hand
  4. Upload the snapshot, revalidate – and start over if follow-up errors appear
→
With the system 2–6 minutes
  1. Fetch the snapshot and read the validation messages
  2. Analyse the error, load the matching data excerpt and rules
  3. Generate a structured correction and check it technically
  4. Apply, write back, revalidate in the target system – with a report

Observations from project operation with snapshots containing few errors – not a controlled measurement and no guaranteed runtime.

Can an AI system not only analyse such data, but correct it in a targeted way – while staying transparent enough for experts to trace every decision?

02The approach

Not a single prompt, but specialised agents.

Complex production data requires different capabilities. Instead of one model that is supposed to do everything, the system divides the work: an orchestrator understands the request and plans, specialists handle knowledge, the planning system and dialogue. When needed, a web search for external knowledge and an email agent that sends reports to the responsible people join in.

Each agent has a clearly defined task, its own tools and exactly the context it needs for it. Hover over the nodes to see who does what.

  • Orchestrator: primary interface to the domain expert, plans the steps and delegates the tasks.
  • RAG Agent: searches production documents and validation rule sets via Azure AI Search.
  • Smart Planning Agent: fetches, checks, corrects and writes back snapshots in the planning system.
  • Chat Agent: answers domain questions and explains error classes.
  • Websearch Agent: only activated when external knowledge from the web is needed.
  • Email Agent: prepares emails with reports and only sends them on explicit instruction.

Breaking up the rulebook

The rulebook contains the domain knowledge for the correction: which rules apply to a detected error and how the correct value can be derived.

Theory: Signal-to-Noise Ratio More signal, less noise
Entire rule set
Matching rule cards
Schematic illustration

Instead of providing the entire rule set for every correction, the knowledge was divided into a shared core and modular rule cards. Depending on the detected error, the system receives exactly the relevant rules – the context stays focused, and it is traceable which rules went into a correction. The rules are written in natural language, so experts can maintain them without programming skills.

The idea behind it: the model should not see everything, but the right things. Less, but more relevant context – more signal, less noise.

03The graph

Complex flows, clearly traceable. The process becomes a graph.

Error classification, context search, rule matching, correction generation, technical check and revalidation are clearly separated nodes. Each one writes its intermediate result into a shared state. This makes it possible to reconstruct afterwards what the model saw and why the flow continued or stopped.

04In operation

From laptop to cloud – with humans in the loop.

The result is not a concept, but a working overall system: deployed on Azure, operated through a web interface and connected to a real production planning system.

A snapshot is loaded, validated, analysed, corrected, written back and then validated again by the target system. Auditability, control and reproducibility were not added afterwards – they shaped the architecture from the start.

05Lessons Learned

What practice has shown.

i

Success needs proof.

A missing error message does not mean a successful run. Only revalidation shows whether a correction actually worked.

ii

The right context decides.

An AI model can only work with the information it receives. What matters are the relevant data, their relationships and the matching rules.

iii

Correction is an iterative process.

One change can reveal further errors. That is why corrections have to be checked again and, if needed, improved over several runs.

iv

Wrong is not the same as hallucinated.

A correction can deviate from the expected reference value and still be justified by the data. Not every deviation is a hallucination.

v

Stable does not mean correct.

An AI system can make the same decision several times and still be wrong. Repeatability alone says nothing about domain correctness.

vi

The application is more than the AI.

Only the interplay of specialised agents, reliable checks, technical interfaces and traceable flows turns AI answers into a usable solution.

06Research · Bachelor’s thesis 2026

How reliably does the system work?

In my bachelor’s thesis, I examined how different AI system architectures affect the correctness, stability and traceability of automated data corrections.

The key finding: The greatest benefit for domain correctness came from the targeted provision of relevant knowledge. Graph-based orchestration mainly improved the traceability of decisions and processes.
